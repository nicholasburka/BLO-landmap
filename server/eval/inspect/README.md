# The inspection eval set

Nick, 2026-09-06: *"how did the llm pass perform? did we informally eval it / test it?"*
The honest answer was **by eye, on four pages, once**. This is what replaced that.

Fourteen real agency pages, captured once and checked in, each with a label written
by hand. `npm run eval:inspect` runs the harvest and the model pass over every one of
them N times and prints how it did. Nothing here is generated by a model except the
answers being scored.

---

## What is in here

| | |
|---|---|
| `pages.json` | The set: a slug, a URL, what shape of page it is, and why it earns its place. Also the pages we tried and **could not** capture, with the reason. |
| `pages/<slug>.html` | The page as the inspector's own guarded fetch saw it, with a `<!-- BLO eval capture -->` header carrying the final URL, the capture date and the byte count. |
| `labels/<slug>.json` | **Hand-written.** What a careful researcher would keep, what they would obviously drop, and what the page says about itself. |
| `golden/<slug>.json` | One real model answer, recorded verbatim with the candidate list it answered about. Feeds an offline test. |
| `results/<date>.json` | What a scored run measured. The next run prints a delta against the most recent one. |
| `capture.ts` | Fetches a page and writes it to `pages/`. The only thing here that touches the network. |
| `run.ts` | The scorer. |
| `harvest.test.ts`, `golden.test.ts` | Offline, in the ordinary suite, free. |

---

## Running it

```bash
cd server
set -a; . ./.env; set +a          # vitest and tsx do not load .env for you

npm run eval:inspect              # 14 pages × 3 runs — about 3 minutes, about $0.70
npm run eval:inspect -- --runs 1
npm run eval:inspect -- --only epa-frs-download
npm run eval:inspect -- --offline # harvest only: no key, no cost, no model
```

`--offline` answers one question — *is every link the label wants even among the
candidates?* — and needs nothing. That same check runs in CI as `harvest.test.ts`,
because a harvester regression would otherwise show up as a lower score with no way
to tell whether the prompt or the harvester caused it.

`--write-golden` records the first run's answer for any page that does not have a
golden yet. Existing goldens are never overwritten: a golden that regenerates itself
asserts nothing.

## Reading the table

```
page                       cand  kept   hit  miss  bad  neut   role   prose   ds  topic    tags  agree      in    out      s   $/page
usda-ers-rucc                12     8   8/8     0    0     0   100%   3.7/5 100%   100%     1/1   1.00    4458    784    6.4  $0.0168
```

- **cand** — links the page offered before pruning.
- **kept / hit / miss** — how many links the pass stored, how many of the label's
  wanted links it found, how many it did not. Averaged over the runs, so `6.7/8`
  means it found seven of eight most of the time.
- **bad** — links it kept that the label explicitly calls distractors (navigation,
  sibling datasets, share links). **neut** — links it kept that the label neither
  wants nor forbids; these count against precision too, because storing a link
  nobody asked for is the link-tree spam this pass exists to prevent.
- **role** — of the links it got right, how many carried the role the label gives them.
- **prose** — labelled prose fields matched (exact or partial) out of the labelled
  total. Partial means one is a substring of the other, or 60% of the label's words
  appear in the answer — the number should measure reading, not phrasing.
- **ds** — `isDataset` correct.
- **topic** — how often it filed the page under the subject the label gives it
  (P5-63). `—` where the label states none, which is the honest answer for a
  page whose own words name no subject.
- **tags** — labelled tags it found, out of the labelled total. The summary line
  carries precision as well: a pass that answers eight tags to hit two has not
  read the page, it has listed the vocabulary.
- **agree** — Jaccard of the kept URL sets across the runs. `1.00` means the three
  runs kept exactly the same links.
- **$/page** — an **estimate** from the token counts at the model's list price. Not a
  bill: it ignores caching and everything else that moves an invoice.

Below the table, every miss, every bad extra and every wrong role is printed with its
URL. That list is the useful part; the summary line is for the ticket.

## The delta

A run writes `results/<date>.json` and compares itself with the most recent earlier
file. Running twice in one day is normal on the day a prompt changes, so the second
file gets a `T<hh-mm>` suffix rather than overwriting the first.

```
Against 2026-09-07 (3 runs, claude-sonnet-5):
  precision +6 pts
  recall    +8 pts
  roles     +2 pts
  isDataset +1.3 pages
  agreement +0.04
  out tok   -102
```

## Adding a page

1. Add it to `pages.json` with a slug, the URL, its shape and why it is worth a slot.
   Prefer a page that is a *kind* the set does not have yet over another example of
   one it does.
2. `npx tsx eval/inspect/capture.ts --only <slug>`. If it fails, the page blocks
   automated clients — move it into `"skipped"` with the reason and pick another.
   (FEMA, BLS and HUD USER all refused us.)
3. **Read the page.** Then write `labels/<slug>.json` by hand. Do not ask a model to
   label it: a label generated by the thing being measured measures nothing.
4. `npm run eval:inspect -- --offline --only <slug>` to check the harvester can see
   everything the label wants.
5. `npm run eval:inspect -- --only <slug> --runs 1 --write-golden` to record a golden.

### Writing a label

```jsonc
{
  "url": "…", "capturedAt": "2026-09-06",
  "isDataset": true,
  "keep": [{ "url": "…", "role": "data-file", "note": "why this one" }],
  "keepUnharvested": [{ "url": "…", "role": "viewer", "why": "the harvester cannot see it" }],
  "drop": ["…"],
  "prose": { "provider": "…", "program": "…", "updateCadence": "…", "coverage": "…", "geography": "…" },
  "topic": "water",
  "tags": ["wells", "drinking-water"],
  "notes": "what makes this page worth scoring"
}
```

- `keep` is every link a careful researcher would want, with the role they would give
  it. Judge the page, not the model.
- `drop` is the **tempting** wrong answers specifically — the sibling dataset, the
  "All Data" nav item, the sample file the page calls a sample. It is not every other
  link: anything in neither list scores as neither, which is the right answer for a
  link that is neither wanted nor a mistake.
- `keepUnharvested` is for a link a researcher wants that the harvester genuinely
  cannot see. Putting it in `keep` would make the harvest test red for a decision we
  made; leaving it out entirely would quietly lower the bar. The test asserts these
  are *still* missing, so the day one starts being harvested it says to promote it.
- Leave a prose field out when the page does not say it. A page with no stated
  cadence is a test of whether the pass invents one.
- `topic` is one id from `src/config/taxonomy.ts` — the subject a careful
  researcher would file the page under — and `tags` are the words they would
  give it. Both follow the prose rule: leave them out when the page's own words
  name no subject. An ArcGIS Hub shell that draws everything in the browser has
  neither, and a label that guessed would score the guess rather than the
  reading.
- `notes` is for the next person. Say what the trap on this page is.

## What P5-63 changed (2026-09-07)

The TIGER directory's 0.60 agreement — fifty equally-good folders against a
twelve-link cap — turned out to be a defect rather than a property of the page.
A bare file index now skips the model for its links entirely and ranks the
folders in code, and the label files gained a hand-written `topic` and `tags`.

| | before | after |
|---|---|---|
| census-tiger-directory · agreement | 0.60 | **1.00** |
| census-tiger-directory · hit | 6.7/8 | **8/8** |
| census-tiger-directory · input tokens | 11,914 | **3,158** |
| overall precision · recall | 85% · 91% | 86% · **93%** |
| overall, excluding the page that ran out of API credit mid-run | 85% · 91% · 0.92 | **92% · 93% · 0.95** |
| topic (new) | — | 7.0/13 pages |
| tags (new) | — | precision 41%, recall 73% |

`results/2026-09-07T02-17.json` is the before, `results/2026-09-07T07-20.json`
the after. The last page of the after run (`usgs-press-release`) lost two of its
three runs to an out-of-credit 400 and fell back to the unranked ranking, which
keeps six links on a page whose right answer is none — which is why the
all-pages line understates the change.

## What the set is for

It is not a benchmark to maximise. Precision and recall trade against each other here
and both are gameable by relabelling. What it is for:

- **Telling a prompt change from a mood.** Three runs and a Jaccard number, so
  "that seems better" can be checked.
- **Catching the silent failures.** The first scored run found the output cap was
  still too low: one page hit it on two runs of three, fell back to the shape-only
  ranking, and lost a third of its recall. Nobody would have seen that by eye.
- **Keeping the record.** `results/` says what the numbers were the day a prompt was
  written, which is the only way a later change can be argued about with evidence.
