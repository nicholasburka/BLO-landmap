# Deploy Runbook — LLM-Enabled BLO National Map

Step-by-step to take `main` live. Two pieces deploy separately:

- **Backend** — the Express LLM proxy in `server/` (Railway / Render / Fly / any Node host).
- **Frontend** — the Vite static build in `dist/` (Netlify).

Do the **backend first** so you have its URL to give the frontend. Everything in this doc is a one-time setup plus a redeploy; later code pushes to `main` just trigger rebuilds.

> Secrets live only in host env settings and gitignored local `.env` files — never commit them.

---

> To run everything on a laptop for a demo or a rehearsal — public map, knowledge base and API against the real bucket, no Postgres — see **docs/RUN-LOCAL.md** (`npm run demo`).

## 0. Prerequisites (once)

- [ ] **Rotate the RentCast API key.** The previous key was committed to git history and shipped in the browser bundle — treat it as compromised. Generate a fresh key in the RentCast dashboard; you'll paste it into the frontend env below. (If listings ever need a *private* key, proxy the calls through the backend instead of shipping it.)
- [ ] Generate a session signing secret and keep it somewhere safe (you'll paste it into the backend env):
  ```bash
  node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
  ```
- [ ] Have your **Anthropic API key** and **Mapbox public token** ready.

## 1. Backend (Express LLM proxy)

The backend lives in the `server/` subdirectory. Point your host at that directory (Railway/Render: set **Root Directory** = `server`).

**Build & start commands:**
- Install: `npm install` (helmet and, since P5-88, `compression` are dependencies — a fresh install is required)
- Build: `npm run build`
- Start: `npm start`

**Environment variables** (Settings → Variables):

| Env | Value | Notes |
|---|---|---|
| `SESSION_HMAC_SECRET` | the 32-byte hex string from step 0 | **Required — server refuses to boot without it.** Not a password; a random secret. |
| `ANTHROPIC_API_KEY` | your Anthropic key | Required — server refuses to boot without it. |
| `NODE_ENV` | `production` | Hardens error responses; force-disables `BUDGET_BYPASS`. |
| `ALLOWED_ORIGINS` | `https://<prod-site>.netlify.app` (comma-add the staging origin if used) | CORS allowlist. Must include every browser origin that calls the API. |
| `SESSION_COOKIE_SAMESITE` | `lax` or `none` *(optional)* | SameSite on the internal session cookie. Default `none` in production, which iOS Safari refuses as a third-party cookie when the API is on a different site from the frontend. Put the API on a subdomain of the site (Railway: `railway domain api.blacklandownership.com --service blo-map-api`, then a CNAME `api` → the target Railway prints, then `VITE_API_URL=https://api.blacklandownership.com` on the frontend and `OAUTH_ISSUER` to match) and set this to `lax`. |
| `TRUST_PROXY_HOPS` | `1` (default) or `2` | Proxy hops between the client and the server. `1` = host proxies directly (Railway/Render). `2` = a CDN sits in front of the host. **Must match reality** or per-IP limits are spoofable. |
| `PORT` | as your host requires | Railway/Render usually inject this automatically. |
| `DATABASE_URL` | Postgres connection string *(optional but recommended)* | Powers the usage dashboard with durable history. Unset = dashboard works but only shows data since the last restart. See "Usage dashboard" below. |
| `PGSSL_CA` | PEM certificate chain *(optional)* | The DB connection **verifies the server certificate by default** (P5-19). Managed hosts with public CAs (Neon, Supabase, Render) need nothing; a host with a private CA (Railway's proxy) gets its CA pasted here. |
| `LIBRARY_ASK_MODEL` | model id (default `claude-sonnet-5`) | Model behind **Ask the knowledge base** (P5-41). Haiku 4.5 (`claude-haiku-4-5-20251001`) is an acceptable cost-saver; answers are cited either way. |
| `LIBRARY_ASK_MAX_TOKENS` | integer (default `1500`) | Output cap per Ask round; ≤ 4 rounds per question (3 tool calls + the final answer). The cap is spent by the thinking block as well as the answer — at 1000 a long-context round could return no text at all, silently (P6-34). Raise rather than lower it: a cap is a ceiling, not a spend. |
| `LIBRARY_SUGGEST_MAX_TOKENS` | integer (default `400`) | Output cap for the filing suggestion made when a link or file is dropped (P5-47). It is four short fields, so this is deliberately small; the model is `LIBRARY_ASK_MODEL`. With no `ANTHROPIC_API_KEY` the drop still works and the entry simply says the assistant was unavailable. |
| `LIBRARY_UPLOAD_MAX_BYTES` | bytes (default `209715200` = 200 MB) | Largest file accepted by the upload API **and** the largest server-side fetch of a dropped link (P5-34/P5-47). A link over the cap fails with "too large (limit …)" on the entry. |
| `EXTRACT_MAX_BYTES` | bytes (default `20971520` = 20 MB) | Largest document whose text is extracted (P5-46). Bigger files are recorded as "too large to read here" and stay download-only; nothing is retried until the file changes. |
| `EXTRACT_MAX_PAGES` | integer (default `400`) | Pages read from one PDF. Beyond this the extraction is marked truncated — the pages that were read are still searchable and citable. |
| `PLACE_FETCH_TIMEOUT_MS` | milliseconds (default `30000`) | How long one request to an outside agency may take when fetching a source for a place (P5-57). A slow layer (FEMA's NFHL is the usual one) reports "took too long" and the reader is told to try a smaller radius. |
| `PLACE_FETCH_MAX_BYTES` | bytes (default `26214400` = 25 MB) | Most one answer from an outside agency may weigh (P5-57), enforced on both the declared length and the bytes that arrive. Sized for a national county CSV; raise it only if a `download`-type source you need is genuinely bigger. |
| `PLACE_REPORT_TIMEOUT_MS` / `PLACE_REPORT_MAX_SOURCES` | milliseconds (default `90000`) / integer (default `50`) | The place report (P5-58) runs every applicable source for one address at six at a time, against one overall deadline: sources still running (or not yet started) when it fires are reported as "could not check in time" rather than failing the whole report, and at most `PLACE_REPORT_MAX_SOURCES` sources are run per report. Finished reports are cached whole at `library/derived/place/<placeKey>.json` for 7 days; `POST /api/library/place/report` with `refresh: true` re-runs everything, slices included. Needs `ANTHROPIC_API_KEY` for the written summary only — without it the findings still come back and the summary is `null`. |
| `INSPECT_TIMEOUT_MS` | milliseconds (default `15000`) | How long ONE probe of a dropped link may take (P5-59) — a `?f=json` for an ArcGIS layer, a Socrata views record, the first bytes of a file, a portal page. A person is waiting on the button, so it is half the fetch-for-a-place budget; over it the entry says "we could not reach the site in time". |
| `INSPECT_MAX_BYTES` | bytes (default `2097152` = 2 MB) | Most one probe reads from a body (P5-59). A probe reads METADATA, never the dataset: an 800 MB CSV is reported as an 800 MB CSV from its headers and the first 64 kB of columns. Raise it only if a portal page you need is genuinely bigger than 2 MB of HTML. |
| `LIBRARY_PRUNE_MAX_TOKENS` | integer (default `6000`) | Output cap for the ONE model call a page inspection makes (P5-61): it reads the page's first ~3,000 characters plus the links harvested off it, and answers with at most 12 of them (each with a role and a one-line reason) plus what the prose said about the publisher, cadence, licence and access. Metered against `DAILY_BUDGET_TOKENS` and billed to the person who dropped the link, exactly like the filing suggestion. **Do not lower it below ~3,000**: the default was 1,500 during the first live check and an EPA page with 18 candidates truncated mid-JSON; at 3,000 the eval set (P5-62) still saw a 23-link USGS page cut off on one run in three, so the default is 6,000. Any fallback now logs one line — `[link-prune] <slug>: <reason>` — and stores the reason as `inspection.pruneError`, which the entry shows. **No `ANTHROPIC_API_KEY` = no call**: the inspection keeps the first 6 candidates by URL shape, marks them `unranked` and says so. |
| `REPLICATE_MAX_BYTES` / `REPLICATE_MAX_ROWS` | bytes (default `104857600` = 100 MB) / integer (default = `TABULAR_MAX_ROWS`, 200,000) | The ceiling on "Replicate now" (P5-59), which copies a whole source into `library/datasets/<slug>/`. Over either one the copy stops, nothing half-written is filed, and the entry's plan falls back to `fetch-on-demand` with a note saying why. Rows are capped where the explorer's parser is, so a copy is never a dataset nobody can open. |
| `PGSSL_NO_VERIFY` | `1` *(avoid)* | Explicit, logged escape hatch that disables certificate verification. Only for a temporary bring-up; never leave it set — an on-path attacker could read session and password hashes. |
| `LIBRARY_DATA_DIR` | path (default `./library-data`) | Working directory for the internal library's mirrored files (phase 5, step 2+). The library's queryable index and auth state live in Postgres via `DATABASE_URL`; without `DATABASE_URL` the server boots with library features disabled and the public map is unaffected. |
| `LIBRARY_BUCKET_ENDPOINT` / `LIBRARY_BUCKET_REGION` / `LIBRARY_BUCKET_NAME` / `LIBRARY_BUCKET_KEY_ID` / `LIBRARY_BUCKET_SECRET` | see "Library object storage" below | S3-compatible object storage for library files (P5-7). All five must be set or library **file** features are disabled (logged at boot); the public map is unaffected either way. |
| `PUBLIC_SITE_URL` | `https://<prod-site>.netlify.app` *(recommended)* | Origin of the frontend, used by the MCP server (P5-50) to make the links in tool results absolute — a desktop assistant cannot open a relative path. Also the fallback source for public dataset files when `county_values` runs on a deployment without the repo's `public/` tree beside it. As of P5-51 it has a second job: it's where the OAuth login detour (see `OAUTH_ISSUER` below) sends a signed-out user to log in before returning them to the authorization request. Unset = relative links, `county_values` reports itself unavailable when the files are absent, and OAuth sign-in cannot complete. See **docs/MCP.md**. |
| `OAUTH_ISSUER` | `https://<backend-host>` *(optional, required only for ChatGPT/Claude connectors)* | The API's own public https origin — no path, no trailing slash. Turns on the OAuth 2.1 authorization server (P5-51) that lets ChatGPT's custom connectors and Claude's remote connectors reach `/mcp` (neither can carry a personal token). It doubles as the base of the MCP resource identifier (`$OAUTH_ISSUER/mcp`), and is deliberately configured rather than derived from the request's `Host` header — a forged `Host` would otherwise redirect a connector's whole flow elsewhere. Must be `https` except on `localhost`/`127.0.0.1` (dev only). Unset = the OAuth endpoints answer `503`/report themselves unavailable and personal tokens keep working exactly as before. See **docs/MCP.md**. |
| `BETA_PASSWORD` | *(leave unset for pure prod)* | Optional normal-tier password. |
| `STAGING_PASSWORD` | *(optional)* | Cap-bypass password for PM testing — see STAGING.md. (No longer the dashboard login — `/dashboard`, `/api/usage`, and `/api/health/usage` use internal accounts as of P5-20.) |
| `DAILY_BUDGET_TOKENS` / `DAILY_BUDGET_TOKENS_PER_IP` | *(unset = defaults 200k / 15k)* | Only override if you know what you're changing. |

- [ ] **Fetch for a place (P5-57)** makes outbound requests to public agency endpoints (EPA, FEMA, USDA, state portals) on behalf of a signed-in user. Every request goes through the same host guard as dropped links — public addresses only, re-checked on each redirect — with a timeout, a byte cap and a limit of 30 requests a minute per source. Cached slices live in the bucket under `library/derived/sources/`, so no egress allowlist or extra credentials are needed; if your host blocks outbound HTTPS, this feature is the one that will notice.
- [ ] **Link inspection (P5-59)** makes outbound requests too, on every dropped link and whenever someone presses "Inspect this link". Same host guard, same redirect re-checks, `INSPECT_TIMEOUT_MS` and a 2 MB read cap — it reads metadata, never the data. "Replicate now" uses the same path with the much larger `REPLICATE_MAX_BYTES`; it is admin-only and queued, so it never holds a request open.
- [ ] **Reading a page for data (P5-61)** changes what an inspection of an ordinary web PAGE does: the HTML the probe already read is scanned for candidate data links (anchors, `<link rel=alternate>`, schema.org `Dataset` distributions, a site `data.json`), and **one metered model call** prunes them to the few that are actually the dataset's data or query endpoints — with a role and a reason each — and reads the page's prose for the publisher, cadence, licence, coverage and access methods. Only the pruned list is stored (`inspection.links`, at most 12); the rest is a count. Nothing new is fetched: the harvest is over bytes already in hand, and a candidate is classified by its URL shape alone. A `/dataset/<slug>` page on a CKAN portal (data.gov and most state portals) skips the model entirely — one guarded `GET /api/3/action/package_show` reads the publisher's own resource list, with `package_search?fq=name:<slug>` behind it (data.gov 404s `package_show` for slugs whose page renders) and the HTML scrape behind that. A page whose publisher ships schema.org `Dataset` structured data also skips the model: its `distribution[]` is already typed, and each link gets a role from its declared format. Budget: see `LIBRARY_PRUNE_MAX_TOKENS`. **Troubleshooting a page that came back `unranked`:** grep the API log for `[link-prune]` — the line names the entry and the reason (no key, rate-limited, cut off at the token cap, not JSON), and the same reason is on the entry as `inspection.pruneError`. The links the pass rejected are kept as `inspection.dropped` (≤ 20 URLs) and the entry can show them.
- [ ] **Do NOT set `BUDGET_BYPASS`.** (It's ignored in production anyway, but don't rely on that.)
- [ ] Deploy. Watch the logs for `BLO API server listening on port …`. If you see a `FATAL:` line instead, a required secret is missing.
- [ ] Note the public backend URL (e.g. `https://blo-map-api-production.up.railway.app`).

### Usage dashboard (optional, recommended)

The backend serves a self-hosted usage dashboard at **`https://<backend-host>/dashboard`** — token/day chart, request counts, unique visitors, top query themes, and a recent-requests table with per-request token cost. It's the "our own dashboard" view of who's using the app and what it costs.

- **Login:** the dashboard uses **internal accounts** (P5-20) — the same username/password sessions as the library, created via the admin CLI above. If you're already logged in on the map site, `/dashboard` loads straight in (the session cookie is shared); otherwise the page offers a login form. The same session gates the `/api/usage` JSON and `/api/health/usage`. The staging password no longer opens any of these.
- **History across redeploys:** set **`DATABASE_URL`** to any managed Postgres. Free tiers that work out of the box: [Neon](https://neon.tech), Railway's own Postgres plugin, Render Postgres, Supabase. The table is created automatically on first boot — no migration step. The dashboard badge reads **"Postgres · history on"** when connected.
- **Without `DATABASE_URL`:** the dashboard still works but shows only data since the last restart (badge: "In-memory · since restart"), and each redeploy resets it.
- **Also in the logs:** every request emits a structured JSON line to stdout (`{"t":"usage",...,"total":<tokens>,...}`) with hashed IPs — greppable in the host log viewer even without the dashboard.
- For authoritative **billed cost**, the Anthropic Console → Usage is still the source of truth; this dashboard tracks request volume and token counts.

To provision Postgres on Railway: add a Postgres plugin to the project, then reference its connection string as `DATABASE_URL` on the API service. On Neon: create a project, copy the pooled connection string, paste it as `DATABASE_URL`, redeploy.

### Library object storage (Backblaze B2)

Library files live in a private B2 bucket (**`blo-library`**, S3-compatible endpoint `https://s3.us-west-000.backblazeb2.com`), chosen in the P5-6 spike for its default-on versioning (every overwrite/delete keeps the prior version — the deletion-protection safety net). The server keeps a local mirror under `LIBRARY_DATA_DIR` and **re-syncs it from the bucket on every boot** — the host disk is assumed ephemeral, so a redeploy loses nothing (bucket + Postgres are the sources of truth). Watch the boot logs for `[library] mirror synced: …`.

- **Server credentials:** use a **bucket-scoped** application key (capabilities: list/read/write/delete/share on `blo-library` only — key name `blo-library-server`), never the account master key. Set the five `LIBRARY_BUCKET_*` envs on the API host.
- **Team direct access:** a separate **read-only** bucket-scoped key (`blo-library-readonly`) can be handed to team members for direct file access (B2 web UI, Cyberduck, or rclone) — if the app is ever down, the files are still there with `meta.json` beside each.
- **Portability:** the server only speaks the generic S3 API with the endpoint from env — moving to R2/S3 later is an env change, not a code change.
- **Dev sync CLI** (P5-13, the "fluid pathway" for cleaning data locally): run from `server/` with the five `LIBRARY_BUCKET_*` envs set (they're in `server/.env` on a dev machine). No external binary — it's the same bucket service the API uses (SAFE_KEY screening, mirror discipline, audit).
  ```bash
  npm run library -- pull      # bucket → local folder (default ./library-local, or $LIBRARY_SYNC_DIR / --dir <path>)
  # ...clean files locally, write datasets/<slug>/meta.json (status, lineage)...
  npm run library -- status    # dry-run diff — read-only, prints changed / remote-only / local-only
  npm run library -- push      # local → bucket, then reindexes the catalog
  ```
  - **Non-destructive by default:** `push` never deletes remote files unless you pass `--delete`; `pull` never deletes local files unless you pass `--prune`. Local copies always stay in place after a push. Even with `--delete`, strays under `library/incoming/` (teammates' app uploads and link drops that your local tree may simply predate) are listed and skipped unless you also pass `--delete-incoming` (P5-19). Dotfiles (`.DS_Store`) and `*.geocode-cache.json` sidecars are never pushed.
  - **Per-user limits:** the heavy internal routes (dataset rows, summaries, exports, ask, layer values, upload, reindex) allow 120 requests per minute per user and answer `429` beyond that; reindex is single-flight (a second click joins the running one). Normal use never gets near either.
  - Unchanged files are skipped by size — except `meta.json` manifests, which are content-compared so a status flip always syncs.
  - `push` reindexes the catalog directly when `DATABASE_URL` is set (pointing at the API's Postgres). Without it, push still uploads and then warns — hit **Reindex** in the app instead (Reindex re-syncs the host mirror and re-reads every manifest fresh from the bucket, so external pushes are always picked up).
  - Malformed `meta.json` or an unknown `status` prints a warning but never blocks the upload — files are the truth; fix and re-push.
- **Wiki pages are files too** (P5-14): flat markdown at `library/wiki/<slug>.md`, no manifest — the page title is its first `# Heading`. They sync with `library pull`/`push` like everything else, so wiki pages can be written/edited in a local editor and pushed (then Reindex, as with any external push). Served via `GET/PUT /api/wiki/:slug` (internal-only; PUT takes raw `text/markdown`, 1 MB cap). In-app editing lives at `/wiki` (P5-15): internal links (`/wiki/…`, `/library/…`) written in a page navigate in-SPA; external links open hardened in a new tab.
- **Saved views are files too** (P5-16): flat JSON at `library/views/<slug>.json` (catalog kind `view`), one document per saved map+query snapshot — name, `savedBy`/`savedAt` (the data-as-of date), the client's opaque `state` (layers/filters/limit/region/prompt/viewport), and a ≤100-row results snapshot for embeds. Served via `GET/POST /api/views` and `GET /api/views/:slug` (internal-only; the server slugifies the name, auto-suffixing collisions). Internal users get a **Save view** control on the map (bottom-left); a shared `/views/<slug>` link is login-guarded and restores the exact layers, query, and viewport for any internal user. Reindex rebuilds view rows from the bucket like everything else.
- **Wiki embed blocks** (P5-17): a fenced code block naming a saved view or catalog entry — ` ```view:<slug> ` or ` ```entry:<slug> ` (the handle the Save-view success note shows) — renders inline in wiki pages as a live card: view cards show the name, data-as-of date, top-5 results, and an **Open in map →** link restoring the saved state; entry cards link into `/library/<slug>`. Pure client feature (markdown renderer + hydration) — nothing extra to deploy; a missing or deleted target degrades to a "not found" note in the page.
- **Dataset explorer** (P5-31): every library entry with a tabular file (`.csv`, `.tsv`, `.json` array of objects, `.geojson`) gets a **Browse data →** link to `/library/<slug>/data` — a paged table with search, click-to-sort, per-column filters, a column chooser, a row drawer, and a schema panel (types, fill rates, top values). The server parses each file once (`GET /api/library/data/:slug` schema, `…/rows` paged rows; internal-tier, bare 401s) and caches the parse in memory; **Reindex** clears that cache, so after an external `library push` hit Reindex as usual. Browse caps: `TABULAR_MAX_BYTES` (default 25 MB) and `TABULAR_MAX_ROWS` (default 200 000) — larger files get a 413 that says to download instead. Wiki pages now index with an empty category (the wiki is the knowledge base, not a category of it).
- **Internal map layers** (P5-18): a `published` dataset whose `meta.json` carries a `layer` block becomes a county choropleth for logged-in users — e.g. `"layer": { "geometry": "county", "file": "target_index.csv", "geoKey": "GEOID", "valueKey": "target_index", "name": "Plan target index", "dataType": "index", "unit": "pts", "direction": "higher_better", "range": { "min": 0, "max": 100 }, "description": "…", "source": "…", "year": 2026 }`. `dataType` ∈ percentage/currency/count/index/years/ordinal; `range` is optional (computed from the data when absent); `file` defaults to the entry's first tabular file; GEOIDs are zero-padded and the `0500000US…` form is accepted. Served by `GET /api/layers/internal` (manifest) and `…/internal/:slug` (values), internal-tier with bare 401s; an invalid block is skipped with one server log line naming the field. The client registers manifest entries into the layer registry after login (ids `internal-<slug>`) and removes them on logout, so the public bundle never contains a layer name, slug, or value (`p518-standin` is a bundle-leak canary). Internal layers score, filter, rank, tooltip, save as views, and embed exactly like public layers. Geometry is county, point (P5-24) or line (P7-3). Reindex after pushing a new or changed layer file, as with any dataset.
- **Enrichment pathway** (P5-23): most new datasets need locations and county FIPS before they can be mapped. From `server/`: `npm run library -- geocode <csv> (--address COL | --city COL --state COL | --lat COL --lng COL | --county COL --state COL) [--out <path> | --in-place] [--dry-run] [--force]` appends `lat`, `lng`, `GEOID` (5-digit county FIPS), `geocode_method`, `geocode_confidence`. Resolution order per row: existing coordinates → county only; county + state names → offline FIPS join against `public/datasets/geographic/county-lookup.json` (Parish / Borough / St. variants normalised, ambiguous names refused); street address → US Census one-line geocoder (coordinates + county, no key); city + state → Nominatim place (1 req/s, `GEOCODE_USER_AGENT` to identify yourself) then Census county. Every answer, including no-match, is cached in `<csv>.geocode-cache.json`, so re-runs are offline and idempotent; existing values are never overwritten without `--force`; the default output is `<name>.geocoded.csv` beside the input. **Provenance convention:** enriched columns travel with `<field>_source` (URL), `<field>_confidence` (`high|medium|low`), and, when sources disagree, `<field>_conflict` (`city` | `street` | `proxy`, combinable with `+`) plus `<field>_alt_location`; the geocoder reads those and emits `<field>_alt_geoid` + `<field>_same_county` (yes/no) — same-county conflicts are acceptable, different-county ones are listed in the report for review. Record the pass in `meta.json.lineage.enriched: [{ field, method, date }]`. Warnings never block (exit 0); unmatched rows are listed with reasons.
- **Internal point layers** (P5-24): a published dataset with `"layer": { "geometry": "point", "file": "organizations.csv", "latKey": "lat", "lngKey": "lng", "labelKey": "Organization", "popupFields": ["Tier", "HQ City", "Website"], "color": "#ff6b1c", "name": "Organizations (HQ)", "description": "…", "source": "…", "year": 2026 }` renders as clustered markers for logged-in users: click a point for a popup of `popupFields` (http links clickable), click a cluster to zoom in. `GET /api/layers/internal/:slug` returns a GeoJSON FeatureCollection whose properties are **only** the label + `popupFields` — every other column stays on the server (`LAYER_MAX_FEATURES` cap, default 20 000; rows with bad coordinates are skipped and counted). Point layers are overlays: they never enter the scoring query, are listed in the Layers tab's Internal section with a color swatch, are captured/restored by saved views (`state.pointLayers`), and are named on wiki embed cards. Sources/layers are namespaced `internal-<slug>-…` and removed on toggle-off and logout.
- **Internal line layers** (P7-3): a published dataset with `"layer": { "geometry": "line", "file": "transmission.geojson", "pathKey": "_path", "labelKey": "NAME", "popupFields": ["OWNER", "VOLTAGE"], "color": "#2b6cb0", "width": 3, "name": "Transmission lines", "description": "…", "source": "…", "year": 2026 }` draws as strokes for logged-in users. **`pathKey` names the column holding the path** — use `_path` for a `.geojson` file, which is the synthetic column the tabular parser now writes from each `LineString`/`MultiLineString` (alongside the `_lng`/`_lat` it already wrote for points); a CSV may instead carry WKT (`LINESTRING (…)` / `MULTILINESTRING ((…),(…))`) or a JSON coordinate array in a column of its own and name that. `width` is 0.5–10 px (default 2). `GET /api/layers/internal/:slug` returns a FeatureCollection of `LineString` (one part) or `MultiLineString` (several), properties **only** the label + `popupFields`, same as a point layer; caps are `LAYER_MAX_FEATURES` (20 000) **and `LAYER_MAX_VERTICES` (default 500 000)** — a few hundred corridors is few rows and can be millions of coordinates, which the row cap cannot see. Rows whose path will not parse are skipped and counted. On the map each line layer gets two Mapbox layers, `internal-<slug>-line-hit` (14 px, invisible, so a 2 px stroke is clickable) and `internal-<slug>-line` on top; hovering widens the line under the pointer, clicking opens the popup **at the click**, and focusing one line (rail row, `?focus=`, chat `show_layer`) **frames that line's own extent** rather than flying to a point on it. - **Bulk analysis pathway** (P7-5): proximity between two layers is the same primitive wherever it runs, but **the cardinality decides the home, not the operation** — 11 sites against one layer is microseconds and belongs in a request; 190,000 brownfields is a batch job. The API's on-demand tier (`POST /api/working-sets/:slug/proximity`, and MCP `measure_proximity`) therefore holds at most **5,000 rows** and **20 million point-to-segment tests**, and past either it **refuses with a sentence naming this pass** rather than crawling — the work is synchronous on one event loop, so a long run makes the whole API unresponsive, not just its own request. For anything bigger, from `server/` over a pulled tree: `npm run library -- proximity <working-set> --to <layer> [--from <dataset>] [--within <miles>] [--id <column>] [--apply] [--dir <path>]`. It reads `library/working-sets/<slug>/meta.json` plus the two datasets, measures great-circle distance point-to-point and **point-to-segment** for a line layer, and writes a derived column onto the set's manifest (plus `derived/<id>.rows.json` with the per-row numbers, and `derived/<id>.json` when a column is over 64 kB). **Dry run by default** — it prints the table and the counts and writes nothing until `--apply`, like `retag` and unlike `geocode`. No bucket, no database, and **no row ceiling**; then `push` and the reindex publishes it with no build and no deploy. The source datasets are never modified: the output is a column on the working set, so provenance stays clean and both sources stay re-fetchable. Dataset A must already carry latitude, longitude and a county FIPS column — the pass refuses with the `geocode` command that makes them rather than reverse-geocoding per row.
- **Weighted indices** (P7-8): a composite index over several of a working set's **county** layers — the public map's Lens, generalised and savable. The on-demand tier is `POST /api/working-sets/:slug/composite` and MCP `build_index`; the formula (`terms`: layer, weight, direction) is stored on the derived column it produces, so re-running reads it back rather than retyping it, and the **same formula over unchanged inputs is served from the manifest with nothing parsed**. Terms may be public registry layers (`pct_Black`) as well as held internal ones, which is what lets a class-and-race index exist at all. The ceiling is **12 layers** and **32 MB of source tables** — checked from the catalog with nothing opened, so a refusal costs no parse — and past it the 413 names this pass: from `server/` over a pulled tree, `npm run library -- index <working-set> --name "<label>" --layer <layer>:<weight>:<direction> --layer … [--id <column>] [--apply] [--dir <path>]`. Dry run by default, no bucket, no database, no ceiling, and the public registry files are read straight off `public/datasets/`. A composite column is also listed in the internal layer manifest as `internal-<set>~<column>`, so it draws as an ordinary county choropleth on 0–100; a proximity column deliberately is not, because nothing in its record says which end of "miles away" is good.

Failures say why in plain words ("the site refused the request", "too large (limit 200 MB)", "not a public address", "took too long"); the entry offers **Try again** (`POST /api/library/catalog/:slug/refetch`, internal-tier, CSRF, per-user limiter). ### Account management (internal library)

Internal-library accounts have **no email flows** — the admin CLI is the only way accounts are created and passwords reset. Run it from `server/` on any machine that can reach the same Postgres the API uses (set `DATABASE_URL` in `server/.env` or the shell):

**Bootstrap:** after the first deploy with `DATABASE_URL` set, create the first admin account with `npm run users -- create <yourname> --role admin` — there is no default account and no signup flow, so until you run this nobody can log in.

**On Railway (production):** the database is on the project's private network, so run the CLI inside the service instead of from a laptop — an empty password line makes it generate one, printed once:

The remote side joins the arguments and runs them as one shell line, so pass the pipeline plainly (no `sh -c`):

```bash
railway ssh --service blo-map-api -- "echo | node dist/cli/users.js create <username> --role admin"   # generates a password, printed once
railway ssh --service blo-map-api -- "echo | node dist/cli/users.js create <username>"                # a regular member
# a chosen password: base64 it locally so no shell can expand a $ or a quote on the way in
B64=$(printf '%s\n' '<password>' | base64)
railway ssh --service blo-map-api -- "echo $B64 | base64 -d | node dist/cli/users.js reset-password <username>"
```

The person then changes it on their Account page (P5-76).

```bash
cd server
npm run users -- create <username> [--role admin|internal]   # prompts for password (hidden), or leave empty to generate one
npm run users -- reset-password <username>                   # also revokes all of their live sessions
npm run users -- disable <username>                          # offboarding: revokes live sessions — their very next request 401s
npm run users -- enable <username>
npm run users -- list                                        # username, role, status, created (never hashes)
```

- **Roles:** `internal` (default) can log in and use the library; `admin` additionally passes admin-gated routes. Usernames are 2–64 chars of letters, digits, `. _ -`; passwords ≥ 8 chars (generated ones are 16).
- **Changing your own password** (P5-76): any logged-in user can do it from **Account → Change password** (`POST /api/account/password`) — no admin needed, and the CLI stays the path only for someone who has *forgotten* theirs. It verifies the current password with the same hash the login uses, enforces the same ≥ 8-character minimum, is capped at **5 attempts per hour per account** (429 after that), writes an `account.password` audit row, and **signs out every other session** for that account — the browser making the change stays signed in.
- **Offboarding = `disable`**, not delete — the account row is kept so the audit trail stays intact.
- Every CLI action is written to `library_audit` (actor `cli`).
- If the CLI prints "Cannot reach the library database", `DATABASE_URL` is unset or wrong — it must point at the **same** Postgres instance as the API service.

**Login protections (no configuration; know they exist before you debug a login):**

- **Per-IP:** 10 login attempts per hour per address → `429`.
- **Per-username:** 20 failed attempts within a rolling hour locks that username for the rest of the window — *including* attempts with the correct password, which return the same generic `401` as any other failure (a guesser must not be able to tell a lockout from a wrong password). A successful login clears the counter. So: "my password is right and I still get 401, and nobody else is affected" = this lockout. The counter is in-process, so an API restart clears it; the 20 `login.failure` rows in `library_audit` (with a salted IP hash and truncated user-agent, never the raw IP or the password) are the durable record.
- **Origin:** a browser `Origin` header that is not in `ALLOWED_ORIGINS` (and is not this host) is rejected by the login route itself, not only by CORS. A cross-origin frontend that logs in *must* be listed in `ALLOWED_ORIGINS` or every login 401s.
- **MCP write access (P5-52):** an assistant can add notes, append to pages, drop links and save views only with the `write` scope — a personal token minted with **Allow writes** ticked on the account page, or an OAuth connection the person granted `write` at the consent screen. Read-only credentials get `insufficient_scope` and the attempt is audited. There is no delete tool, and every write lands two `library_audit` rows (the change and the `mcp.<tool>` call) carrying `detail.via` — the client's name — which is what puts "… via ChatGPT" on the activity feed. Revoking the token or disconnecting the app from **Account** cuts it off immediately. See **docs/MCP.md** section 6.
- **Session cookies** are `Secure` whenever the request arrived over HTTPS (via `X-Forwarded-Proto`, so `TRUST_PROXY_HOPS` must be right) and `SameSite=None` only when `NODE_ENV=production`. Logging in again revokes the previous session. Sessions dead (expired or revoked) for more than 7 days are deleted from `library_sessions` once per boot.

## 2b. Step-1 security gate (what CI/local checks prove before any internal feature ships)

Phase 5 adds an internal, login-gated tier on top of the public map. Before each release, the **Step-1 gate** must be green — it is the automated proof that the public map is unregressed and the auth boundary holds:

| Check | Command | What it proves |
|---|---|---|
| Auth 401 sweep | `cd server && npx vitest run src/__tests__/authSweep.test.ts` | Walks the real Express router table; **every** registered route that is not in the explicit public set (`/api/health`, `/api/session`, `/api/auth`, `/api/login`, the dashboard shell) must return a bare `401` unauthenticated — including with a forged session cookie — and every mutating route must return `403 forbidden` with a valid session but no CSRF header. A new route is guarded or the test fails; there is no allowlist to forget (P5-19). |
| Bundle-leak check | `npm run build` (runs automatically as `postbuild`; standalone: `npm run check:bundle-leaks`) | Greps `dist/` for a canary list of internal-only strings (cookie name, DB table names, dev credentials, bucket name, dataset slugs, and **content words** such as the initiative name — maintained in `scripts/check-bundle-leaks.mjs`), and requires every file under `dist/datasets/` to be a git-tracked public dataset. Fails the build if internal code or content reaches the world-readable client bundle (P5-19). |
| Public-map regression | `npm run test:e2e` | Full Cypress suite against its own build in `dist-e2e/` (API base = the preview origin, so stubbed internal specs work) — map loads, layers toggle, onboarding works, the chat page against a stubbed stream. Leaves `dist/` untouched. |
| Server + frontend units | `cd server && npx vitest run` / `npx vitest run` | Login/session/CSRF behavior, middleware denials, UI auth state. |
| `noindex` on internal routes | in `netlify.toml` | `/login` and `/account` send `X-Robots-Tag: noindex, nofollow` — the internal entrance stays out of search results. |

A new route is guarded by default: only routes listed in the sweep's public set may answer without a session, so adding one there is a deliberate, reviewable act. If you add internal subject matter (a dataset family, an initiative), add a canary for it in `scripts/check-bundle-leaks.mjs` in the same PR — the gate catches only what it knows.

## 5. Known one-time blip at cutover

The token signing secret changed in this release. Any returning user holding a token from an older build gets **one** silent 401 on their next action, then the client auto-re-mints and shows "Session refreshed — please send that again." It self-heals on the next send — no action needed, just don't be alarmed by a brief 401 blip in logs right after deploy.

## Scaling note (later, not now)

The rate-limit and budget counters are in-memory per process, so they reset on each backend redeploy and don't share state across replicas. Fine for a single instance. Before scaling the backend horizontally, move both to Redis (the code comments mark where).
